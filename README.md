# Django-tasks-service

Сервис задач, который использует [Django-auth-service](https://github.com/9ZonDG6/Django-auth-service)
для аутентификации. У него своя БД задач, а пользователей и паролей в ней нет.
Владелец задачи определяется по `user_id` из проверенного access-токена.

## Запуск

Нужны Python 3.14+ и uv. Сначала запусти сервис авторизации на порту 8000
по инструкции в его README. Затем в этом проекте:

```bash
uv sync --locked
cp .env.example .env
uv run python manage.py migrate
make server
```

API будет доступен по адресу http://127.0.0.1:8001/api/tasks/.
Оба приложения запускаются отдельно, используют отдельные базы и окружения.

## Первый запрос

Зарегистрируй пользователя через `/users/register/` сервиса авторизации или
используй существующего. Получи токен:

```bash
curl -X POST http://127.0.0.1:8000/auth/login/ \
  -H 'Content-Type: application/json' \
  -d '{"username": "alice", "password": "Example-Pass-92!"}'
```

Скопируй поле `access` из ответа и создай задачу:

```bash
curl -X POST http://127.0.0.1:8001/api/tasks/ \
  -H 'Authorization: Bearer <access-token>' \
  -H 'Content-Type: application/json' \
  -d '{"title": "Проверить два сервиса", "description": "Вход через общий auth"}'

curl http://127.0.0.1:8001/api/tasks/ \
  -H 'Authorization: Bearer <access-token>'
```

## API

Все запросы требуют access-токен. Список содержит только задачи текущего пользователя
и разбит на страницы по 50 записей (`count`, `next`, `previous`, `results`).

| Метод | Адрес | Действие |
| --- | --- | --- |
| GET | `/api/tasks/` | Список своих задач |
| POST | `/api/tasks/` | Создание задачи |
| GET | `/api/tasks/<uuid>/` | Просмотр задачи |
| PATCH / PUT | `/api/tasks/<uuid>/` | Обновление задачи |
| DELETE | `/api/tasks/<uuid>/` | Удаление задачи |

Редактируются `title` (до 200 символов), `description` и `completed`.
`id`, `owner_id`, `created_at` и `updated_at` заполняет сервер. Переданный клиентом
`owner_id` игнорируется. Чужая задача возвращает `404` при чтении, изменении и удалении.

## Проверка токенов

Сервис получает публичные ключи из JWKS и проверяет подпись **RS256**, `kid`,
издателя `iss`, срок `exp`, время выдачи `iat` и `token_type=access`.
Обязательны также `jti` и UUID пользователя в `user_id`.
Refresh-токен для доступа к задачам не подходит.

JWKS кэшируется в каждом процессе на 5 минут. Таймаут получения ключей — 5 секунд.
Адрес ключей берётся только из настроек, а не из заголовков присланного токена.
Неверный токен возвращает `401`; недоступность JWKS при необходимости загрузить
ключи — `503`. Уже закэшированные ключи используются до истечения кэша.

Роли не дают обхода проверки владельца: даже staff/superuser видит только свои задачи.
Выход, смена пароля и отключение пользователя в auth не отзывают access здесь мгновенно:
сервис проверяет токен без обращения к БД пользователей. Выданный access может действовать
до истечения срока (по умолчанию 15 минут). Обновление токенов выполняется только в auth.

## Настройки

| Переменная | Значение по умолчанию / назначение |
| --- | --- |
| `AUTH_JWKS_URL` | `http://127.0.0.1:8000/auth/jwks.json` |
| `AUTH_JWT_ISSUER` | `django-template-auth`, должен совпадать с `JWT_ISSUER` в auth |
| `AUTH_JWT_AUDIENCE` | Пустое; ожидаемое назначение токена при включённом audience |
| `DATABASE_URL` | SQLite локально; для PostgreSQL — `postgres://user:password@host:5432/tasks` |
| `SECRET_KEY` | Секрет Django; локальный пример не использовать в production |
| `DEBUG` | В `.env.example` включён для разработки |
| `ALLOWED_HOSTS` | Хосты сервиса |

Для проверки audience задай `JWT_AUDIENCE=tasks-service` в сервисе авторизации,
а здесь — `AUTH_JWT_AUDIENCE=tasks-service`. Перезапусти оба приложения и получи
новые токены. При заданной аудитории токены без неё или с чужой аудиторией отклоняются.
По умолчанию принимаются текущие токены auth без `aud`; токены с заданным `aud`
требуют настройки ожидаемой аудитории здесь.

Для развёртывания нужны HTTPS, свой `SECRET_KEY`, `DEBUG=false`, реальные хосты,
рабочая БД и доступный HTTPS-адрес JWKS. `runserver` предназначен для разработки;
WSGI-приложение — `config.wsgi:application`. Приватный RSA-ключ сюда не передаётся.

## Проверки

```bash
make check
```

Тесты поднимают локальный HTTP JWKS-сервер и подписывают токены временным RSA-ключом.
Проверяются CRUD, изоляция владельцев, кэш ключей, неверная подпись, срок, издатель,
audience, тип токена, неизвестный ключ и недоступный JWKS.

Дополнительно можно проверить контракт с настоящим кодом соседнего auth-проекта:

```bash
AUTH_SERVICE_DIR=/path/to/Django-auth-service uv run pytest tests/test_auth_contract.py -q
```

У auth-проекта должны быть установлены зависимости в `.venv` и настроены ключи
в `.env`. Тест использует отдельную БД в памяти, выполняет регистрацию, вход и
обновление через Django test client и проверяет полученные токены в tasks.
В этом тесте транспорт JWKS подменён ответом настоящего auth-эндпоинта;
HTTP-загрузка и кэш отдельно проверяются остальными тестами.
